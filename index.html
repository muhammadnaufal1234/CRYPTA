ENKRIPSI

Pengaman Pesan & File

Aplikasi web yang mengenkripsi pesan dan file dengan AES-256-GCM, menurunkan kunci dari kata sandi lewat PBKDF2, dan mengecek keutuhan file dengan SHA-256. Semuanya berjalan di peramban tanpa server.

Cara Kerja

Apa yang sebenarnya terjadi di balik setiap klik tombol. Pilih prosesnya untuk melihat langkah-langkahnya.

Tujuan: mengubah pesan atau file menjadi data acak yang hanya bisa dibuka oleh orang yang tahu kata sandinya.

  1. 1

    Pengguna memasukkan data dan kata sandi

    Pesan teks diubah menjadi deretan byte (UTF-8). File dibaca langsung sebagai byte. Kata sandi hanya disimpan di memori selama proses berjalan.

    "Halo" → 48 61 6c 6f
  2. 2

    Membangkitkan salt dan IV acak

    Peramban membuat salt 16 byte dan IV (nonce) 12 byte dengan generator acak kriptografis (crypto.getRandomValues). Keduanya selalu baru setiap kali enkripsi, sehingga pesan yang sama tidak pernah menghasilkan ciphertext yang sama.

    salt 9f2c41…a71e IV 4be0d2…13d8
  3. 3

    Menurunkan kunci dengan PBKDF2

    Kata sandi tidak dipakai langsung sebagai kunci. Kata sandi dan salt diolah dengan PBKDF2-HMAC-SHA256 sebanyak 200.000 kali sampai menjadi kunci AES 256 bit. Proses yang sengaja lambat ini membuat penyerang hanya bisa mencoba sedikit tebakan per detik.

    kata sandi + salt → 200.000× HMAC-SHA256 → kunci 256-bit
  4. 4

    Enkripsi dengan AES-256-GCM

    Data dienkripsi dengan AES-256 dalam mode GCM. Hasilnya ada dua: ciphertext (data teracak, panjangnya sama dengan data asli) dan authentication tag 16 byte, semacam segel yang dihitung dari ciphertext dan kunci.

    plaintext + kunci + IV → ciphertext + tag
  5. 5

    Menyusun paket keluaran

    Salt, IV, dan ciphertext+tag digabung menjadi satu paket. Untuk teks, paket diubah ke Base64 supaya bisa disalin ke chat atau surel. Untuk file, paket disimpan sebagai berkas .enc. Salt dan IV boleh terlihat orang lain karena keduanya bukan rahasia. Rahasianya hanya kata sandi.

Tujuan: mengembalikan data asli, sekaligus memastikan data tidak diubah sedikit pun sejak dienkripsi.

  1. 1

    Pengguna memasukkan paket dan kata sandi

    Teks Base64 diubah kembali menjadi byte, atau file .enc dibaca sebagai byte. Data yang terlalu pendek atau Base64 yang rusak langsung ditolak.

  2. 2

    Memecah paket

    Karena formatnya tetap, aplikasi tahu persis di mana tiap bagian berada: 16 byte pertama adalah salt, 12 byte berikutnya adalah IV, dan sisanya adalah ciphertext beserta tag.

    byte 0–15 byte 16–27 byte 28–…
  3. 3

    Menurunkan ulang kunci

    Kata sandi yang diketik dan salt dari paket diolah lagi dengan PBKDF2 200.000 iterasi. Kata sandi dan salt yang sama pasti menghasilkan kunci yang sama. Kata sandi berbeda menghasilkan kunci yang sama sekali lain.

  4. 4

    Dekripsi dan verifikasi tag

    AES-GCM menghitung ulang tag dari ciphertext dan kunci, lalu mencocokkannya dengan tag di paket. Perubahan satu bit saja di ciphertext, tag, IV, atau salt membuat tag tidak cocok.

    ✓ Tag cocokPlaintext ditampilkan atau file asli diunduh.
    ✗ Tag tidak cocokMuncul pesan galat dan tidak ada data yang dikeluarkan.
  5. 5

    Kenapa kata sandi salah dan data rusak tidak dibedakan?

    Dua-duanya membuat tag tidak cocok, dan memang sengaja tidak dibedakan. Penyerang jadi tidak mendapat petunjuk apa pun tentang bagian mana yang salah.

Tujuan: memastikan sebuah file tidak berubah, misalnya file yang diunduh atau hasil dekripsi. Hash tidak memakai kata sandi dan tidak bisa dibalik.

  1. 1

    Memilih file

    File dibaca sebagai deretan byte di peramban. File tidak diunggah ke mana pun.

  2. 2

    Menghitung SHA-256

    Seluruh byte file diproses fungsi hash SHA-256 dan menghasilkan sidik digital 256 bit, ditampilkan sebagai 64 karakter heksadesimal. File sekecil atau sebesar apa pun selalu menghasilkan panjang yang sama.

    file → SHA-256 → 3a7bd3e2…42dd4f1b
  3. 3

    Efek longsoran (avalanche)

    Mengubah satu bit saja pada file menghasilkan hash yang benar-benar berbeda, bukan sekadar mirip. Karena itu perubahan sekecil apa pun pasti terlihat.

    "abc" → ba7816bf8f01cfea…"abd" → a52d159f262b2c6d…
  4. 4

    Membandingkan hash

    Hash dibandingkan dengan hash yang ditempel pengguna (misalnya dari pengirim) atau dengan hash file kedua.

    ✓ COCOKFile identik, tidak berubah.
    ✗ BEDAFile sudah berubah atau rusak.

Istilah Penting

Kamus singkat untuk memahami cara kerja aplikasi.

Plaintext
Data asli yang masih bisa dibaca, misalnya pesan atau isi file.
Ciphertext
Hasil enkripsi berupa data acak yang tidak bisa dibaca tanpa kunci.
AES-256
Standar enkripsi simetris dari NIST dengan blok 128 bit dan kunci 256 bit. Kunci yang sama dipakai untuk enkripsi dan dekripsi.
GCM
Mode operasi AES yang sekaligus mengenkripsi dan menghasilkan tag autentikasi, jadi data sekaligus dirahasiakan dan dijaga keutuhannya.
PBKDF2
Fungsi yang mengubah kata sandi menjadi kunci dengan HMAC berulang ribuan kali, sehingga tebakan brute force menjadi lambat.
Salt
Nilai acak 16 byte yang dicampur ke kata sandi. Mencegah serangan tabel pelangi (rainbow table), karena kata sandi yang sama menghasilkan kunci berbeda.
IV / Nonce
Nilai acak 12 byte yang wajib unik untuk setiap enkripsi dengan kunci yang sama. Membuat ciphertext selalu berbeda.
Authentication tag
Segel 16 byte dari GCM. Jika ada data yang diubah, tag tidak cocok dan dekripsi ditolak.
SHA-256
Fungsi hash satu arah yang menghasilkan sidik digital 256 bit. Dipakai untuk mengecek keutuhan file.
Base64
Cara menulis data biner sebagai teks (A–Z, a–z, 0–9, +, /) supaya bisa disalin. Base64 bukan enkripsi.

Kenapa Aman?

🔑
Kunci tidak pernah disimpan

Kunci dibuat ulang dari kata sandi setiap kali dibutuhkan. Tidak ada kunci atau kata sandi yang tersimpan.

🐢
Tebakan dibuat lambat

200.000 iterasi PBKDF2 membuat setiap tebakan kata sandi butuh waktu, sehingga brute force sangat mahal.

🛡️
Manipulasi terdeteksi

Tag GCM memastikan data yang diubah satu bit pun langsung ditolak, tidak diam-diam menghasilkan data rusak.

💻
Tanpa server

Semua proses berjalan di peramban dengan Web Crypto API. Tidak ada data yang dikirim, jadi tidak ada yang bisa bocor dari server.

Pertanyaan Umum

Apakah data saya dikirim ke server?

Tidak. Semua proses berjalan di peramban memakai Web Crypto API. Halaman tidak melakukan permintaan jaringan apa pun dengan data Anda.

Bagaimana jika saya lupa kata sandi?

Data tidak bisa dipulihkan. Kata sandi tidak disimpan di mana pun, dan tanpa kata sandi kunci AES tidak bisa diturunkan kembali. Simpan kata sandi Anda dengan baik.

Kenapa mengenkripsi pesan yang sama hasilnya selalu berbeda?

Setiap enkripsi memakai salt dan IV acak yang baru. Ini disengaja agar penyerang tidak bisa mengenali pesan yang sama dari ciphertext-nya.

Apa bedanya enkripsi dengan hash?

Enkripsi bisa dibalik dengan kata sandi yang benar. Gunanya merahasiakan isi. Hash tidak bisa dibalik dan tidak memakai kata sandi. Gunanya memastikan file tidak berubah.

Berapa ukuran file maksimal?

Aplikasi diuji untuk file hingga sekitar 50 MB, karena seluruh file diproses di memori peramban.

Apakah aplikasi ini siap dipakai untuk data produksi?

Aplikasi ini bersifat edukatif untuk mata kuliah Kriptografi dan belum melalui audit keamanan tingkat produksi.
